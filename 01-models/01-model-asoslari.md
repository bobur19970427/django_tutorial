# 1. Model asoslari

## 1.1. Model nima?

**Model** — bu ma'lumotlar bazasidagi **jadval (table)** ning Python dagi ko'rinishi.

| Python (Django)       | Ma'lumotlar bazasi (SQL) |
|-----------------------|--------------------------|
| Model class           | Jadval (table)           |
| Field (atribut)       | Ustun (column)           |
| Model instance        | Qator (row)              |
| `Model.objects`       | Jadvalga so'rovlar       |

Django **ORM** (Object-Relational Mapping) bizga SQL yozmasdan, Python kodi orqali bazada ishlash imkonini beradi.

```python
# SQL:
# SELECT * FROM blog_post WHERE is_published = true ORDER BY created_at DESC;

# Django ORM:
Post.objects.filter(is_published=True).order_by("-created_at")
```

## 1.3. Birinchi model

`blog/models.py`:

```python
from django.db import models


class Post(models.Model):
    title = models.CharField(max_length=200)
    body = models.TextField()
    is_published = models.BooleanField(default=False)
    created_at = models.DateTimeField(auto_now_add=True)

    def __str__(self):
        return self.title
```

Har bir model:
- `django.db.models.Model` dan meros oladi;
- har bir class atributi (`models.XxxField`) — jadvaldagi ustun;
- `__str__` — admin panel va shell da obyekt qanday ko'rinishini belgilaydi (doim yozing!).

### Django avtomatik nima qo'shadi?

1. **`id` field** — agar siz `primary_key=True` bo'lgan field yozmasangiz, Django avtomatik qo'shadi:
   ```python
   id = models.BigAutoField(primary_key=True)
   ```
   `pk` — bu har doim primary key ga ishora qiluvchi alias (`post.pk == post.id`).

2. **`objects` manager** — bazaga so'rov yuborish uchun: `Post.objects.all()`.

3. **Jadval nomi** — `<app_label>_<model_name_kichik_harfda>` → `blog_post`.

## 1.4. Migratsiyalar

Migratsiya — modeldagi o'zgarishlarni bazaga yetkazuvchi "versiya nazorati" fayli.

```bash
python manage.py makemigrations          # model o'zgarishlaridan migratsiya fayli yaratadi
python manage.py makemigrations blog     # faqat bitta app uchun
python manage.py migrate                 # migratsiyalarni bazaga qo'llaydi
python manage.py showmigrations          # qaysi migratsiya qo'llangan / qo'llanmagan
python manage.py sqlmigrate blog 0001    # migratsiya qanday SQL yaratishini ko'rsatadi
python manage.py makemigrations --check --dry-run   # CI uchun: migratsiya qolib ketmaganmi?
python manage.py migrate blog 0002       # ma'lum migratsiyaga qaytish (rollback)
python manage.py migrate blog zero       # app ning barcha migratsiyalarini bekor qilish
```

### `sqlmigrate` bilan tekshirish (advanced odat)

```bash
$ python manage.py sqlmigrate blog 0001
BEGIN;
CREATE TABLE "blog_post" (
    "id" bigint NOT NULL PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    "title" varchar(200) NOT NULL,
    "body" text NOT NULL,
    "is_published" boolean NOT NULL,
    "created_at" timestamp with time zone NOT NULL
);
COMMIT;
```

E'tibor bering:
- `default=False` SQL da **yo'q**! Django `default` ni **Python darajasida** qo'llaydi, bazada emas (bazada default kerak bo'lsa → `db_default`, 2-darsga qarang).
- Barcha ustunlar `NOT NULL` — chunki `null=False` default holat.

### Migratsiya "tuzoqlari"

| Muammo | Sabab | Yechim |
|--------|-------|--------|
| `makemigrations` "No changes detected" | App `INSTALLED_APPS` da yo'q yoki `migrations/__init__.py` yo'q | Tekshiring |
| Mavjud jadvalga `null=False` field qo'shsangiz Django default so'raydi | Eski qatorlar uchun qiymat kerak | `default=` bering yoki avval `null=True` qilib, keyin data migration |
| Jamoada migratsiya conflict | Ikki kishi bir vaqtda `0005_...` yaratgan | `python manage.py makemigrations --merge` |
| Migratsiya fayllarini o'chirib yuborish | — | **Hech qachon** production dagi migratsiyalarni o'chirmang |

## 1.5. Shell da ishlash (CRUD)

```bash
python manage.py shell
```

```python
from blog.models import Post

# CREATE
p = Post(title="Salom", body="Matn")
p.save()                                   # INSERT
p = Post.objects.create(title="Ikkinchi", body="...")   # bir qatorda

# READ
Post.objects.all()
Post.objects.get(pk=1)                     # topilmasa DoesNotExist, ko'p bo'lsa MultipleObjectsReturned
Post.objects.filter(is_published=True)
Post.objects.first()

# UPDATE
p.title = "Yangi nom"
p.save()                                   # UPDATE (barcha ustunlarni yozadi!)
p.save(update_fields=["title"])            # faqat title ni yangilaydi — tezroq va xavfsizroq
Post.objects.filter(pk=1).update(title="X")  # save() chaqirilMAYDI, signal ishlamaydi

# DELETE
p.delete()
Post.objects.filter(is_published=False).delete()
```

> **Advanced eslatma:** `QuerySet.update()` va `QuerySet.delete()` — bitta SQL so'rov. Ular modelning `save()` metodini **chaqirmaydi** va `pre_save/post_save` signallari **ishlamaydi** (`delete()` da esa signallar ishlaydi, lekin modelning override qilingan `delete()` metodi chaqirilmaydi).

## 1.6. Model qayerda yashaydi? Katta loyihalarda tuzilma

Model ko'payib ketsa, `models.py` ni paketga aylantiring:

```
blog/
  models/
    __init__.py
    post.py
    comment.py
    tag.py
```

`blog/models/__init__.py`:

```python
from .post import Post
from .comment import Comment
from .tag import Tag

__all__ = ["Post", "Comment", "Tag"]
```

Django modellarni `blog.models` modulidan qidiradi, shuning uchun `__init__.py` da import qilish **shart**.

## 1.7. Model nomlash qoidalari (best practices)

- Model nomi — **birlik shaklda**, `PascalCase`: `Post`, `OrderItem` (`Posts` emas).
- Field nomi — `snake_case`: `created_at`, `is_active`.
- Boolean fieldlar `is_`, `has_`, `can_` bilan boshlansin: `is_published`, `has_discount`.
- Vaqt fieldlari `_at` (datetime) yoki `_on`/`_date` (date) bilan tugasin.
- `ForeignKey` nomiga `_id` qo'shmang: `author` deb yozing, Django o'zi `author_id` ustunini yaratadi.
- Field nomi Python kalit so'zlari (`class`, `from`) bo'lmasin va `__` (ikki pastki chiziq) bo'lmasin — u lookup uchun band (`title__icontains`).
- Field nomi `pk` bo'lishi mumkin emas, `_` bilan tugashi ham mumkin emas.
